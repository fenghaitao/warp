# Keep Warp TUI's Local Boundary Narrow

**The best architecture is not a Slipstream-style replacement backend, but a narrowly scoped TUI local mode that sends only `POST /ai/multi-agent` to `crates/warp_local_server`, never asks Warp for an access token, and leaves history, permissions, and tool execution in the client.** Slipstream is the strongest Rust reference for Warp protocol coverage and a partial no-cloud service, while OpenWarp supplies the cleanest precedent for selecting a local channel with `NoAuth` instead of emulating Firebase. The newer client forks prove that Warp's inherited agent controller can execute local-model tool calls without Warp inference, but transplanting their client-side engines would duplicate the compatibility server already implemented here. Harp remains useful only as a hybrid cloud proxy, and the small Python DeepSeek proxy demonstrates the fragility of blanket auth and GraphQL mocks. For the first working TUI, the local server should stay stateless and narrow: the client already replays task history, and the server already handles DeepSeek reasoning and tool-result continuation more faithfully than Slipstream. The implementation should therefore add an explicit, loopback-only local-agent URL, a no-auth multi-agent transport branch, and a login-free TUI readiness path guarded so no other Warp service call can silently use the local server or reach Warp cloud.

## Four project families expose one clear boundary

The reviewed projects solve different problems despite sharing the label “local Warp.” **Slipstream is a downstream product fork with a stateful compatibility backend; OpenWarp is an independent adapter coupled to small client patches; Harp is a selective cloud-preserving interception proxy; and the client forks move provider translation directly into Warp.** Treating them as interchangeable would obscure the main architectural decision: whether local inference should live behind Warp's existing Protobuf/SSE boundary or inside the client.

| Project | Where inference lives | Cloud/auth posture | Agent/tool completeness | Best lesson for this checkout |
|---|---|---|---|---|
| `pixelkaiser/slipstream` | Rust Axum sidecar speaking Warp Protobuf/SSE and OpenAI-compatible Chat Completions | Broad GUI no-cloud mode plus partial local GraphQL; TUI still enters Warp device login | Broad request decoding, client tools, MCP bridging, summaries, SQLite transcripts; weak DeepSeek reasoning preservation | Reuse protocol codecs and targeted no-cloud routing patterns, not the fork or its global server-root rewrite |
| `sasuke39/openwarp` | Go adapter with native and versioned sidecar agent runtimes | Local channel explicitly selects `AuthToken::NoAuth` and skips onboarding | Text, reasoning, client tools, task steering/cancellation, optional harnesses and persistence | Reuse the explicit local-channel/no-auth pattern and future runtime boundary |
| `Achiral-AI/harp` | FastAPI interceptor backed by LiteLLM | Continues to proxy auth, GraphQL, telemetry, and login to Warp | Text-only local turns; tool results and local tool synthesis remain unsupported | Use only for an optional hybrid proxy mode, never as the login-free foundation |
| `loongee/warp-local-proxy` | Small FastAPI DeepSeek translator | Blanket mock auth and hard-coded GraphQL replies | Three tools, in-memory reasoning state, acknowledged mapping gaps | Evidence that mocks can bootstrap a client, and that they become a schema-maintenance trap |
| `man-brain/warp` | Provider-neutral engine and large Warp-Protobuf adapter inside the client | Existing `skip_login` synthetic identity plus explicit Warp-API denial | Shared TUI works; client reconstructs history, tools, MCP, reasoning, and response events | Best current TUI isolation precedent, but do not copy its duplicate agent engine |
| Zap / Loom | Multi-provider engines inside divergent GUI forks | Always-local auth facade in Zap; account-free local/BYOK with optional hosted fallback in Loom | Broad provider and tool support; no modern `crates/warp_tui` | Reuse strict route ownership and inherited client-tool execution concepts only |

Slipstream is the closest server-side analogue. Its Axum service implements `/ai/multi-agent`, passive suggestions, local autocomplete, a deliberately finite `/graphql/v2` facade, health/session routes, and SQLite persistence. It decodes Warp Protobuf requests and emits URL-safe-base64 Protobuf `ResponseEvent`s over SSE, including coherent terminal errors and a broad set of client-executed tool calls ([Slipstream server](https://github.com/pixelkaiser/slipstream/blob/3de21ef37fa93b3602cfe68b8c04d407052a5c39/crates/local_multi_agent_service/src/server.rs); [response mapping](https://github.com/pixelkaiser/slipstream/blob/3de21ef37fa93b3602cfe68b8c04d407052a5c39/crates/local_multi_agent_service/src/response.rs)). Yet its no-cloud claim is materially GUI-specific: the `byok` branch does not patch the current TUI login flow, and its TUI still derives readiness from Warp `AuthState` and opens device authorization when logged out ([TUI login implementation](https://github.com/pixelkaiser/slipstream/blob/3de21ef37fa93b3602cfe68b8c04d407052a5c39/app/src/tui/mod.rs); [TUI OSS entrypoint](https://github.com/pixelkaiser/slipstream/blob/3de21ef37fa93b3602cfe68b8c04d407052a5c39/crates/warp_tui/src/bin/oss.rs)). Slipstream is therefore a valuable protocol corpus, not proof of a completed login-free TUI.

OpenWarp reaches the desired account boundary more directly. Its local client patch chooses `AuthToken::NoAuth` for `Channel::Local`, skips onboarding, and explicitly documents that its adapter does not implement Firebase; the server then concentrates on multi-agent inference and local support routes rather than impersonating Warp identity ([NoAuth patch](https://github.com/sasuke39/openwarp/blob/main/patches/0003-skip-firebase-auth-local.patch); [client guide](https://github.com/sasuke39/openwarp/blob/main/WARP_CLIENT.md)). Its Go adapter also offers cancellation, steering, client tools, DeepSeek-style reasoning, and a versioned NDJSON runtime protocol for alternative harnesses ([server](https://github.com/sasuke39/openwarp/blob/main/cmd/server/main.go); [runtime protocol](https://github.com/sasuke39/openwarp/blob/main/internal/agentruntime/README.md)). This separation is the strongest model for a future multi-harness extension, though it is unnecessary for the initial DeepSeek path.

The remaining projects clarify what to avoid. Harp preserves cloud login by forwarding almost everything except eligible inference requests, and its locally synthesized transaction does not create Warp tool calls ([architecture](https://github.com/Achiral-AI/harp/blob/main/docs/architecture.md); [local handler](https://github.com/Achiral-AI/harp/blob/main/src/harp/hijack.py)). The Python local proxy returns broad success/empty responses and hard-coded GraphQL data, which suppresses immediate errors while converting contract drift into later state failures ([server mocks](https://github.com/loongee/warp-local-proxy/blob/master/server.py); [GraphQL mocks](https://github.com/loongee/warp-local-proxy/blob/master/handlers/graphql.py)). Man-brain, Zap, and Loom prove a selected local model can feed Warp-native tool actions back into the inherited approval/execution controller, but they implement provider translation inside the client; adopting those engines here would create two sources of truth for streaming, reasoning, and tool-call conversion ([man-brain adapter](https://github.com/man-brain/warp/blob/2f7576e71081118939fbd4c66aa38fd25277eecd/app/src/ai/agent/api/local_adapter.rs); [Zap stream](https://github.com/zerx-lab/zap/blob/8954864e335187aecb2b2319050adc8c4da256df/app/src/ai/agent_providers/chat_stream.rs); [Loom local dispatcher](https://github.com/rustcor-foundry/loom/blob/8d7e9d71cf82511a64f2afe722ac4b6e0de72bc9/app/src/ai/agent/api/local_llm.rs)).

## The existing Rust server should remain authoritative

**`crates/warp_local_server` already occupies the right seam: Warp request Protobuf enters, DeepSeek-compatible streaming occurs behind the seam, and Warp response events return over SSE.** The current Warp multi-agent client already understands that wire format, while its inherited controller owns permission prompts, terminal/file tool execution, task history, and the subsequent tool-result request. This is a stronger boundary than embedding another provider engine in `app/`, because the server can evolve its DeepSeek handling without entangling TUI rendering or auth state ([local server README](../crates/warp_local_server/README.md); [local server router](../crates/warp_local_server/src/lib.rs)).

Slipstream should not replace this server. Although its decoder covers more context types and tools, its provider loop treats `reasoning`, `reasoning_content`, and `reasoningContent` primarily as a fallback: normal content clears the buffered reasoning, it does not emit first-class Warp `AgentReasoning` events, and it does not preserve reasoning across a tool-result continuation ([Slipstream provider stream](https://github.com/pixelkaiser/slipstream/blob/3de21ef37fa93b3602cfe68b8c04d407052a5c39/crates/local_multi_agent_service/src/provider.rs)). The server in this checkout was deliberately built around those DeepSeek semantics, along with redirect/credential restrictions, bounded bodies and streams, bounded concurrency, typed validation, and disconnect cancellation. **The correct reuse strategy is selective parity work after the first live TUI turn**, especially Slipstream's request-context decoder, fragmented tool-call tests, MCP name disambiguation, additional tool codecs, and later summary compaction—not a wholesale port of its GraphQL, SQLite, or process-manager layers ([Slipstream request decoder](https://github.com/pixelkaiser/slipstream/blob/3de21ef37fa93b3602cfe68b8c04d407052a5c39/crates/local_multi_agent_service/src/request.rs); [MCP dispatch rule](https://github.com/pixelkaiser/slipstream/blob/3de21ef37fa93b3602cfe68b8c04d407052a5c39/crates/local_multi_agent_service/src/response.rs#L941-L964)).

Server-side persistence is also premature. Slipstream's SQLite transcript store and OpenWarp's bounded conversation files solve restart recovery, summarization, and background-memory use cases, but a Warp client that submits complete task history already has an authoritative transcript ([Slipstream store](https://github.com/pixelkaiser/slipstream/blob/3de21ef37fa93b3602cfe68b8c04d407052a5c39/crates/local_multi_agent_service/src/store.rs); [OpenWarp persistence](https://github.com/sasuke39/openwarp/blob/main/cmd/server/main.go)). Adding a second transcript now would introduce reconciliation and privacy questions without enabling the first local turn. Persistence becomes justified only when context compaction, cross-client resume, or durable background tasks enter scope.

The licensing and maturity signals reinforce selective reuse. Slipstream's backend is AGPL-3.0-only and test-rich but young, macOS-first, and deeply divergent; OpenWarp's adapter is MIT and has current releases and broad tests; Harp is AGPL and intentionally incomplete; the small Python proxy has no standard license and should not be copied ([Slipstream licensing](https://github.com/pixelkaiser/slipstream/blob/3de21ef37fa93b3602cfe68b8c04d407052a5c39/README.md#L82-L86); [OpenWarp license](https://github.com/sasuke39/openwarp/blob/main/LICENSE); [Harp license](https://github.com/Achiral-AI/harp/blob/main/LICENSE); [Python proxy repository](https://github.com/loongee/warp-local-proxy)). Architecture and independently reimplemented patterns are safer than cherry-picking fork-wide diffs; any direct reuse still needs normal license and attribution review.

## Local mode must separate inference from identity

The present client seam explains why setting `SERVER_ROOT_URL` is unsafe. `warp_multi_agent_client::generate_multi_agent_output` derives its endpoint from global `ChannelState::server_root_url`, calls `get_or_refresh_access_token`, and resolves ambient headers before opening the event stream ([current multi-agent client](https://github.com/warpdotdev/warp/blob/7cef787ea0e14073c907e7628ddb8d1a720222b5/crates/warp_multi_agent_client/src/lib.rs)). A global root override would also redirect unrelated auth, GraphQL, update, sharing, telemetry, and account calls toward a server that intentionally exposes only `/health` and `/ai/multi-agent`. **The local inference URL must therefore be a separate transport target, not a new global Warp server root.**

The recommended boundary has four independently auditable responsibilities. A TUI startup option such as `WARP_LOCAL_AGENT_URL=http://127.0.0.1:8787` selects local mode and is validated as loopback HTTP. The multi-agent client selects `{url}/ai/multi-agent` only for that mode and omits access-token refresh, authorization, team, and ambient headers while reusing its existing request encoding, SSE decoding, and cancellation. TUI startup enters an explicit local-ready state without device authorization, and AI capability checks allow the agent only because local mode is active. Finally, a centralized cloud-access guard makes account-dependent calls fail locally or become intentional no-ops; no call may silently fall back to Warp services.

The identity implementation has a short-term and a cleaner long-term form. **For the first integration, the existing `skip_login` machinery is the smallest proven mechanism**: it installs a validated synthetic user, causing the shared TUI login state to proceed directly to terminal creation; man-brain confirms that Cargo feature unification makes this work with the modern headless TUI ([upstream auth state](https://github.com/warpdotdev/warp/blob/7cef787ea0e14073c907e7628ddb8d1a720222b5/crates/warp_server_auth/src/auth_state.rs); [man-brain TUI](https://github.com/man-brain/warp/blob/2f7576e71081118939fbd4c66aa38fd25277eecd/app/src/tui/mod.rs)). It must be scoped to an explicit local TUI build or runtime mode and paired with the cloud guard, because a synthetic user can accidentally satisfy unrelated account feature checks. The cleaner follow-up is a distinct local-ready capability/phase that unlocks terminal and agent interaction without asserting a Warp account at all. That makes Drive, sharing, teams, billing, and account settings unavailable by construction rather than by scattered exceptions.

Configuration should keep credentials on the server side. The TUI needs the local server URL and, at most, a deterministic local model label; `warp_local_server` should continue reading the DeepSeek key from its environment and choosing the provider model at startup ([local server configuration](../crates/warp_local_server/README.md)). This avoids moving provider secrets into Warp settings or sending them as local request headers. It also keeps the trust boundary simple: a loopback client talks to a loopback server, and the server alone talks to the configured provider.

## A five-stage implementation minimizes hidden cloud coupling

The wiring should advance as a sequence of narrow candidates rather than beginning with a fake backend. The sequence below keeps each failure attributable to one boundary and follows what the comparison establishes about the current code.

| Stage | Implementation candidate | Required proof before advancing |
|---|---|---|
| Transport selection | Introduce a typed local multi-agent target/config and parse the TUI-only URL; never mutate `ChannelState::server_root_url` | Unit tests reject credentials/non-loopback hosts as intended and preserve hosted routing when unset |
| No-auth request path | Teach `warp_multi_agent_client` to post the same Protobuf to the local endpoint without token refresh or ambient/team headers | Mock-server test asserts exact path, content type, absence of Warp authorization headers, SSE decode, and cancellation |
| Login-free TUI readiness | Scope `skip_login` or a local-ready phase to explicit TUI local mode; create the initial terminal/session immediately | TUI model/render test starts on the usable surface without a device-login URL while ordinary mode remains unchanged |
| Capability isolation | Disable passive suggestions and unsupported advanced inputs; centralize denial/no-op behavior for account-only startup traffic | Instrumented test or local run shows no Internet connection to Warp and produces explicit errors for unsupported features |
| Live agent loop | Run `warp_local_server`, start TUI in local mode, send a prompt that causes a client tool call, approve/execute it, and observe the resumed DeepSeek response | Recorded end-to-end verification demonstrates reasoning, tool call, typed result continuation, completion, and cancellation |

This order deliberately postpones local GraphQL. If runtime tracing reveals a TUI startup request that cannot simply be disabled, Slipstream's finite dispatcher offers a better pattern than a catch-all: recognize the exact operation, return a typed local result, and report unsupported operations loudly ([Slipstream GraphQL dispatcher](https://github.com/pixelkaiser/slipstream/blob/3de21ef37fa93b3602cfe68b8c04d407052a5c39/crates/local_multi_agent_service/src/graphql.rs)). The same demand-driven rule applies to process supervision. An explicit separately launched `warp_local_server.exe` plus `/health` is sufficient for first wiring; Slipstream's bundled-child manager becomes useful only when packaging convenience outweighs the added restart, configuration, and lifecycle surface ([Slipstream manager](https://github.com/pixelkaiser/slipstream/blob/3de21ef37fa93b3602cfe68b8c04d407052a5c39/app/src/local_multi_agent/mod.rs)).

Verification must test absence as carefully as presence. A successful answer does not prove that token refresh, telemetry, model-catalog lookup, or another startup task avoided Warp. The transport test should inspect headers; the TUI test should prove the login state; and the live run should capture outbound destinations. Man-brain's explicit Warp-API denial posture is stronger than relying on observation alone because it turns future regressions into immediate errors ([fully-local commit](https://github.com/man-brain/warp/commit/92b7a7f9ddc531a7030d2bc450d708be2c148507)). The local mode should likewise be fail-closed: if a request is not owned by the local inference path, it must not opportunistically fall back to hosted inference.

## Conclusion

The comparison changes the problem from “build enough Warp cloud locally” to “remove cloud assumptions at one client seam.” That inversion keeps `warp_local_server` small, makes authentication bypass explicit, and preserves the most valuable part of Warp—the mature client-side agent, permission, terminal, and tool loop—without inheriting a fork-wide maintenance burden.

A successful first release should be judged by a strict invariant rather than feature count: **with local mode enabled, one TUI agent/tool round trip completes through DeepSeek while zero requests require a Warp identity or reach a Warp service.** Once that invariant is enforced in tests, Slipstream and OpenWarp provide a disciplined backlog for incremental protocol parity, process supervision, compaction, MCP, and alternative runtimes without weakening the boundary.
