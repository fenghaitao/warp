# Warp-compatible local backends and proxies (as of 2026-10-03)

## What architecture, protocols, endpoints, providers, tools, authentication, and persistence does each project implement?

### Takeaway

The projects divide into three materially different designs: Slipstream is the broadest Rust no-cloud fork/backend; OpenWarp is a substantial Go backend paired with explicit client patches that remove cloud authentication; Harp is a deliberately partial inference interceptor that still depends on Warp cloud identity and APIs. `loongee/warp-local-proxy` is the closest small Python prototype to our Rust compatibility server, but it is much less complete and has no reusable license.

### Cited Findings

#### 1. `pixelkaiser/slipstream` — full no-cloud fork plus embedded Rust backend

- **Verified in source:** Slipstream adds a Rust `local_multi_agent_service` crate that accepts Warp Protobuf requests, calls an OpenAI-compatible `/chat/completions` endpoint, and returns base64url-encoded Protobuf `ResponseEvent`s over SSE. Its documented endpoints are `/health`, `/ai/multi-agent`, `/ai/passive-suggestions`, `/ai/local-command-autocomplete`, `/graphql/v2`, and shared-session redirects; the Axum router contains those routes. — [service README](https://github.com/pixelkaiser/slipstream/blob/byok/crates/local_multi_agent_service/README.md); [router source](https://github.com/pixelkaiser/slipstream/blob/byok/crates/local_multi_agent_service/src/server.rs)
- **Verified in source:** Provider configuration is OpenAI-compatible rather than DeepSeek-specific. The code calls `{base_url}/chat/completions` and `{base_url}/models`, passes bearer authentication, supports optional `chat_template_kwargs.enable_thinking`, parses both `reasoning` and `reasoning_content`, and assembles streamed function calls. — [provider source](https://github.com/pixelkaiser/slipstream/blob/byok/crates/local_multi_agent_service/src/provider.rs)
- **Verified in source:** The backend exposes nine client-side tools: `read_files`, `file_glob`, `grep`, `search_codebase`, `run_shell_command`, `apply_file_diffs`, `suggest_plan`, `read_mcp_resource`, and `call_mcp_tool`; MCP calls are normalized through `call_mcp_tool`, while an exact direct MCP tool name is accepted only when request context disambiguates it. — [service README](https://github.com/pixelkaiser/slipstream/blob/byok/crates/local_multi_agent_service/README.md); [provider tool definitions](https://github.com/pixelkaiser/slipstream/blob/byok/crates/local_multi_agent_service/src/provider.rs)
- **Verified in source:** Its local GraphQL implementation is intentionally targeted rather than a complete Warp cloud clone. It handles integration records, generic string/cloud objects, user/settings/model-choice queries, and AI-conversation listing, while returning an explicit `unsupported_operation` error for unknown operations. — [GraphQL dispatcher](https://github.com/pixelkaiser/slipstream/blob/byok/crates/local_multi_agent_service/src/graphql.rs)
- **Verified in source:** It persists integration/config objects and AI conversation transcripts in SQLite via Diesel, while the client continues to own other local application state. The README says compatible provider transcripts are reloaded after restart and rewritten after `/compact`. — [store implementation](https://github.com/pixelkaiser/slipstream/blob/byok/crates/local_multi_agent_service/src/store.rs); [service README](https://github.com/pixelkaiser/slipstream/blob/byok/crates/local_multi_agent_service/README.md)
- **Verified in source:** Slipstream wires a no-cloud client mode before startup, permits a local server-root override in that mode, clears cloud session-sharing unless explicitly configured, and sends model discovery without an auth token in no-cloud mode. The repository also retains a `skip_login` feature whose test credentials map to `AuthToken::NoAuth`. — [client startup wiring](https://github.com/pixelkaiser/slipstream/blob/byok/app/src/lib.rs); [AI client path](https://github.com/pixelkaiser/slipstream/blob/byok/app/src/server/server_api/ai.rs); [auth state](https://github.com/pixelkaiser/slipstream/blob/byok/crates/warp_server_auth/src/auth_state.rs); [credentials](https://github.com/pixelkaiser/slipstream/blob/byok/crates/warp_server_auth/src/credentials.rs)
- **Project claim, consistent with the inspected code:** The fork describes itself as no-cloud by default, storing conversations, integrations, connectors, and diagnostics locally and routing tools/MCP through the local backend. — [project README](https://github.com/pixelkaiser/slipstream/blob/byok/README.md)

#### 2. `sasuke39/openwarp` — independent Go adapter plus a patched Warp client

- **Verified in source:** OpenWarp's backend is a Go HTTP server. It registers `/ai/multi-agent`, `/health`, `/signup/remote`, `/login/remote`, settings/profile/memory routes, and task cancel/steer/status routes (both unprefixed and under `/api/v1`). Unlike Slipstream, it does not expose a GraphQL catch-all or local GraphQL service in the server router. — [server router and implementation](https://github.com/sasuke39/openwarp/blob/main/cmd/server/main.go)
- **Verified in source:** The native engine translates Warp Protobuf/SSE to OpenAI Chat Completions, supports streaming text, DeepSeek-style `reasoning_content`, client tool round trips, cancellation/steering, and a server-side `update_task_list`. The accepted client tools include file reads/search/glob, shell start/output/control transfer, file diffs, and codebase search. — [server implementation](https://github.com/sasuke39/openwarp/blob/main/cmd/server/main.go); [LLM adapter](https://github.com/sasuke39/openwarp/blob/main/internal/llm/llm.go); [task-list implementation](https://github.com/sasuke39/openwarp/blob/main/cmd/server/tasklist.go)
- **Verified in source:** Provider configuration is a generic OpenAI-compatible base URL, API key, model, output cap, and optional thinking disable flag. The default adapter listens on `127.0.0.1:18888`. — [configuration source](https://github.com/sasuke39/openwarp/blob/main/internal/config/config.go)
- **Verified in source:** OpenWarp also defines a versioned NDJSON sidecar protocol for alternative agent runtimes. Built-in driver names are `native`, `pi-agent`, and `deepseek-harness`; sidecars exchange turn start/resume/cancel/shutdown plus assistant/tool/todo/terminal events. — [runtime config](https://github.com/sasuke39/openwarp/blob/main/internal/config/config.go); [runtime protocol documentation](https://github.com/sasuke39/openwarp/blob/main/internal/agentruntime/README.md); [DeepSeek harness bridge](https://github.com/sasuke39/openwarp/tree/main/integrations/deepseek-harness); [Pi Agent bridge](https://github.com/sasuke39/openwarp/tree/main/integrations/pi-agent)
- **Verified in source:** Cloud identity is avoided by client modification, not by emulating Firebase. Patch `0003` selects `AuthToken::NoAuth` on `Channel::Local`; other patches select the local channel and skip onboarding. The build guide explicitly says this is required because the local adapter does not implement Firebase endpoints. — [NoAuth patch](https://github.com/sasuke39/openwarp/blob/main/patches/0003-skip-firebase-auth-local.patch); [client patch guide](https://github.com/sasuke39/openwarp/blob/main/WARP_CLIENT.md); [onboarding patch](https://github.com/sasuke39/openwarp/blob/main/patches/0006-skip-onboarding-for-local-adapter.patch)
- **Verified in source:** Conversation history is kept in memory and written to `conversations.json` (bounded to 100 conversations); the optional memory subsystem uses Markdown memory/session files and a SQLite durable work queue. — [conversation persistence](https://github.com/sasuke39/openwarp/blob/main/cmd/server/main.go); [memory store](https://github.com/sasuke39/openwarp/blob/main/internal/memory/store.go); [SQLite queue](https://github.com/sasuke39/openwarp/blob/main/internal/memory/queue.go)
- **Verified in source:** A separate local MCP bridge exposes saved local/SSH execution contexts to Codex or Claude Code through stdio-to-Unix-socket IPC with per-server command/upload/download policy. This is external-agent access to OpenWarp's execution context, not a replacement for Warp's own MCP request protocol. — [MCP implementation](https://github.com/sasuke39/openwarp/tree/main/internal/remotemcp); [MCP setup documentation](https://github.com/sasuke39/openwarp/blob/main/docs/external-mcp/setup.md)
- **Project claim, partly ahead of one documentation page:** The README claims model profiles, three harnesses, local/SSH tools, and an MCP bridge; however, `docs/guide/supported-tools.md` still lists MCP and subagents as unsupported. The source contains the external MCP bridge, so the apparent conflict is scope/version drift rather than evidence that native Warp-agent MCP calls are complete. — [README](https://github.com/sasuke39/openwarp/blob/main/README.md); [supported-tools page](https://github.com/sasuke39/openwarp/blob/main/docs/guide/supported-tools.md); [MCP source](https://github.com/sasuke39/openwarp/tree/main/internal/remotemcp)

#### 3. `Achiral-AI/harp` — transparent cloud proxy with selective local inference

- **Verified in source:** Harp is a FastAPI reverse proxy. It owns `/healthz`, `/stats`, and `POST /ai/multi-agent`; every other method/path is forwarded to `app.warp.dev`, except browser-facing auth/account URLs that receive a 302 to Warp's real site. — [server wiring](https://github.com/Achiral-AI/harp/blob/main/src/harp/server.py); [proxy](https://github.com/Achiral-AI/harp/blob/main/src/harp/proxy.py); [auth redirect](https://github.com/Achiral-AI/harp/blob/main/src/harp/auth_redirect.py)
- **Verified in source:** Harp parses the same Warp Protobuf request and emits the same base64url Protobuf-over-SSE shape, but its locally synthesized response is the minimum text-chat transaction: stream init, begin transaction, create task/message, append text, commit, done. It does not synthesize Warp tool calls. — [architecture](https://github.com/Achiral-AI/harp/blob/main/docs/architecture.md); [hijack implementation](https://github.com/Achiral-AI/harp/blob/main/src/harp/hijack.py)
- **Verified in source:** Current local eligibility covers a single user query and text-only resumed/follow-up history. Tool-result, ambient/cloud, code-review, and passive-suggestion flows are unsupported locally; in `hijack`/`local-only` they produce a valid local error event rather than tool execution. Read-only tools are still a roadmap item. — [eligibility implementation](https://github.com/Achiral-AI/harp/blob/main/src/harp/hijack.py); [roadmap](https://github.com/Achiral-AI/harp/blob/main/docs/roadmap.md)
- **Verified in source:** Provider routing is delegated to a separate LiteLLM container. The bundled config defines Ollama as `local-primary`, Anthropic/OpenAI/Gemini fallbacks, and context-window fallbacks; any OpenAI-compatible backend can be substituted through LiteLLM. — [LiteLLM config](https://github.com/Achiral-AI/harp/blob/main/litellm/config.yaml); [Compose stack](https://github.com/Achiral-AI/harp/blob/main/docker-compose.yml)
- **Verified in source:** Harp does **not** remove cloud identity dependencies. Its stated normal flow signs in through Warp, transparently proxies auth/GraphQL/telemetry, and redirects browser login to `app.warp.dev`. Its single client patch only lets `Channel::Oss` honor a server URL override. — [architecture](https://github.com/Achiral-AI/harp/blob/main/docs/architecture.md); [client patch](https://github.com/Achiral-AI/harp/blob/main/patches/0001-allow-oss-channel-server-url-override.patch)
- **Verified in source:** Harp has no durable conversation database. It derives recent text history from each Warp request and keeps a bounded, short-TTL project snapshot (`HarpCache`) built from a read-only mounted root; the roadmap lists conversation persistence as future work. — [HarpCache implementation](https://github.com/Achiral-AI/harp/blob/main/src/harp/harpcache.py); [roadmap](https://github.com/Achiral-AI/harp/blob/main/docs/roadmap.md)
- **Project claim:** Harp describes three modes (`proxy`, `hijack`, `local-only`) and positions itself as a selective cost/privacy shim, not a full backend. Its published savings percentages are estimates/claims, not demonstrated by repository benchmarks, and should not be treated as verified performance data. — [README](https://github.com/Achiral-AI/harp/blob/main/README.md)

#### 4. `loongee/warp-local-proxy` — small direct-DeepSeek mock backend

- **Verified in source:** This Python/FastAPI prototype implements `/ai/multi-agent`, `/graphql/v2`, catch-all `/api/v1/auth/*`, `/api/v1/*`, and `/ai/*` mocks, plus `/health`; it translates Warp Protobuf/SSE to DeepSeek/OpenAI-compatible streaming. — [server](https://github.com/loongee/warp-local-proxy/blob/master/server.py); [multi-agent handler](https://github.com/loongee/warp-local-proxy/blob/master/handlers/multi_agent.py); [GraphQL mocks](https://github.com/loongee/warp-local-proxy/blob/master/handlers/graphql.py)
- **Verified in source:** It advertises only `run_shell_command`, `read_files`, and `apply_file_diffs`, stores DeepSeek reasoning only in process memory, and acknowledges incomplete diff mapping and no advanced Warp cloud surfaces. — [DeepSeek adapter](https://github.com/loongee/warp-local-proxy/blob/master/deepseek_client.py); [README limitations](https://github.com/loongee/warp-local-proxy/blob/master/README.md)
- **Verified in source:** Its auth behavior is blanket success/empty-JSON mocking rather than a real local identity model, and its GraphQL model/quota responses are hard-coded. That can suppress some startup errors but is fragile when the client changes response schemas. — [server mocks](https://github.com/loongee/warp-local-proxy/blob/master/server.py); [GraphQL mocks](https://github.com/loongee/warp-local-proxy/blob/master/handlers/graphql.py)

#### Excluded after inspection

- `Xchat1/Warp2Api` is the reverse direction: it exposes an OpenAI-compatible API to third-party clients, converts those requests to Warp Protobuf, and calls Warp's hosted AI using JWT/anonymous authentication. It is useful protocol-reading material but is not a local provider backend for the Warp client and does not remove cloud identity. — [README](https://github.com/Xchat1/Warp2Api/blob/master/README.md); [OpenAI-facing router](https://github.com/Xchat1/Warp2Api/blob/master/protobuf2openai/router.py); [Warp API client](https://github.com/Xchat1/Warp2Api/blob/master/warp2protobuf/warp/api_client.py)
- `HappyDongD/warp` is also an OpenAI-facing proxy to Warp cloud, augmented with automated Warp account registration/pooling and token refresh. Its architecture is contrary to the offline/local-provider goal and should not be incorporated into TUI wiring. — [README](https://github.com/HappyDongD/warp/blob/master/README.md); [account pool](https://github.com/HappyDongD/warp/blob/master/pool_service.py); [Warp upstream client](https://github.com/HappyDongD/warp/blob/master/warp2protobuf/warp/api_client.py)

### Inferences

- Slipstream is the closest reference for a **broad Rust local backend**, because it already contains protocol translation, multiple UI-support endpoints, a narrow local GraphQL surface, persistence, autocomplete, and MCP-related tool mapping in the same Warp-derived workspace.
- OpenWarp is the closest reference for **how to avoid cloud identity cleanly**: patch the client transport/auth state to select `NoAuth` for the local channel and skip onboarding, rather than constructing an ever-growing fake Firebase/GraphQL backend.
- Harp is appropriate only for a hybrid mode where signing into Warp and forwarding other cloud traffic is acceptable. Its architecture conflicts with the requirement that the TUI work locally without Warp cloud identity.
- `loongee/warp-local-proxy` validates that a tiny mock surface can make some client builds advance, but blanket mocks are a maintenance trap and add less value than the client-side local-mode approach.

### Gaps

- This review inspected source and repository metadata but did not execute each third-party client/backend pair end to end. Project claims about packaging, actual daily usability, and claimed local-serving ratios remain unverified.
- OpenWarp's public documentation has scope drift around “MCP support”; its external MCP bridge is present, but native Warp-agent MCP parity is not clearly established.
- The exact minimum cloud-free GraphQL/startup surface needed by the new Warp TUI may differ from the GUI-oriented projects; route tracing during TUI launch is still required.

## How complete and maintained is each project, and what licensing or reuse constraints apply?

### Takeaway

Slipstream and OpenWarp are the only candidates with substantial implementation breadth and active release/test signals. Harp is well-structured but intentionally incomplete and has seen no visible development since its initial April 2026 work. The small Python mock has neither tests nor a standard license, so it should be treated as read-only reference material.

The repo was created in April 2026 and presents itself as a maintained downstream fork, although a fork of Warp carries ongoing merge burden. — [backend source/test directory](https://github.com/pixelkaiser/slipstream/tree/byok/crates/local_multi_agent_service/src); [v0.1.36 release](https://github.com/pixelkaiser/slipstream/releases/tag/v0.1.36); [release list](https://github.com/pixelkaiser/slipstream/releases)

Code copied from the backend therefore carries AGPL obligations; reuse inside this Warp workspace is likely license-aligned with the repository's AGPL portion, but distribution obligations still need normal legal review. — [licensing statement](https://github.com/pixelkaiser/slipstream/blob/byok/README.md#licensing); [AGPL license](https://github.com/pixelkaiser/slipstream/blob/byok/LICENSE-AGPL); [MIT license](https://github.com/pixelkaiser/slipstream/blob/byok/LICENSE-MIT)

### Inferences

- For implementation guidance, weight OpenWarp and Slipstream most heavily; they show the most complete agent loops and the strongest maintenance/test signals.
- Prefer OpenWarp for directly reusable snippets when equivalent functionality is not already available in Rust because its adapter is MIT. Prefer Slipstream as an architectural/Rust reference, but track copied code as AGPL-derived.
- Do not copy from `loongee/warp-local-proxy` or `Xchat1/Warp2Api` without obtaining an explicit license grant.
- Harp's limited recent activity and explicit roadmap make it unsuitable as the main backend, though isolated designs (transparent byte forwarding, bounded project context, valid local SSE errors) remain useful references.

### Gaps

- GitHub activity is not the same as maintainer capacity; none of these projects publishes a support SLA or compatibility matrix against every Warp TUI revision.
- No legal opinion was obtained. The license notes above describe repository declarations, not a definitive compatibility determination.
- Release artifacts and test suites were inspected but not independently reproduced in this research task.

## What should we reuse, and can we avoid implementing Warp cloud identity APIs?

### Takeaway

Yes: avoid implementing cloud identity APIs. Wire the TUI to a distinct local inference transport and use a local/no-auth client state, following OpenWarp's `Channel::Local`/`AuthToken::NoAuth` pattern and Slipstream's no-cloud startup path. Then add only the narrow non-inference routes that runtime tracing proves the TUI actually needs.

### Cited Findings

- OpenWarp explicitly bypasses Firebase for local inference and skips onboarding in client patches because its server does not implement Firebase endpoints. This is direct evidence that a client-side local mode is the intended escape hatch in that design. — [NoAuth patch](https://github.com/sasuke39/openwarp/blob/main/patches/0003-skip-firebase-auth-local.patch); [onboarding patch](https://github.com/sasuke39/openwarp/blob/main/patches/0006-skip-onboarding-for-local-adapter.patch); [client guide](https://github.com/sasuke39/openwarp/blob/main/WARP_CLIENT.md)
- Slipstream similarly establishes local/no-cloud defaults before client startup, routes GraphQL to its local service, and avoids attaching auth to local model-discovery calls. This shows how a broader no-cloud mode can be layered without pretending that the local server is a full Warp account service. — [startup wiring](https://github.com/pixelkaiser/slipstream/blob/byok/app/src/lib.rs); [AI client path](https://github.com/pixelkaiser/slipstream/blob/byok/app/src/server/server_api/ai.rs); [local service README](https://github.com/pixelkaiser/slipstream/blob/byok/crates/local_multi_agent_service/README.md)
- Harp takes the opposite approach: it forwards auth, GraphQL, telemetry, and login to Warp cloud and therefore cannot satisfy a login-free/offline TUI by itself. — [architecture](https://github.com/Achiral-AI/harp/blob/main/docs/architecture.md); [server catch-all](https://github.com/Achiral-AI/harp/blob/main/src/harp/server.py)
- Blanket fake auth and empty JSON responses, as used by `loongee/warp-local-proxy`, have no schema guarantees and do not model identity state. They should be a last-resort compatibility shim, not the foundation of local TUI mode. — [mock handlers](https://github.com/loongee/warp-local-proxy/blob/master/server.py); [GraphQL mocks](https://github.com/loongee/warp-local-proxy/blob/master/handlers/graphql.py)

#### Actionable reuse priorities for `crates/warp_local_server`

1. **TUI wiring first — reuse the pattern, not a fake account backend.** Add an explicit local-agent mode/URL in TUI startup; in that mode select `NoAuth`, suppress login/onboarding/refresh, and keep permission/tool execution in the client. OpenWarp's two small auth/onboarding patches are the clearest reference, while Slipstream shows the wider no-cloud startup sequence. — [OpenWarp patches](https://github.com/sasuke39/openwarp/tree/main/patches); [Slipstream startup](https://github.com/pixelkaiser/slipstream/blob/byok/app/src/lib.rs)
2. **Keep the current server narrow until traces demand more.** Slipstream's GraphQL dispatcher is a useful menu of likely operations, but it deliberately errors on unknown operations rather than returning arbitrary empty JSON. If TUI startup calls GraphQL, implement only the observed operations with typed responses. — [Slipstream GraphQL](https://github.com/pixelkaiser/slipstream/blob/byok/crates/local_multi_agent_service/src/graphql.rs)
3. **Port protocol hardening from Slipstream selectively.** Particularly useful areas are OpenAI stream fragmentation, orphan/incomplete tool-result filtering, reasoning-field aliases, model discovery/context-window metadata, and MCP tool-name disambiguation. These overlap our direct DeepSeek path and can be translated or compared test-for-test. — [provider implementation](https://github.com/pixelkaiser/slipstream/blob/byok/crates/local_multi_agent_service/src/provider.rs); [provider tests](https://github.com/pixelkaiser/slipstream/blob/byok/crates/local_multi_agent_service/src/provider_tests.rs)
4. **Consider OpenWarp's MIT runtime boundary for future harness support.** Its versioned NDJSON driver lets the Warp transport remain stable while Pi Agent or DeepSeek Harness owns the agent loop. This is cleaner than continuously expanding one compatibility handler if multiple harnesses become a goal. — [runtime protocol](https://github.com/sasuke39/openwarp/blob/main/internal/agentruntime/README.md); [runtime implementation](https://github.com/sasuke39/openwarp/tree/main/internal/agentruntime)
5. **Borrow persistence only when client-carried history is insufficient.** OpenWarp's bounded `conversations.json` plus SQLite memory queue and Slipstream's SQLite transcript store solve restart/background-memory needs, but they are not required for a TUI that round-trips complete history. — [OpenWarp persistence](https://github.com/sasuke39/openwarp/blob/main/cmd/server/main.go); [OpenWarp queue](https://github.com/sasuke39/openwarp/blob/main/internal/memory/queue.go); [Slipstream store](https://github.com/pixelkaiser/slipstream/blob/byok/crates/local_multi_agent_service/src/store.rs)
6. **Use Harp ideas only as optional modules.** Its byte-preserving reverse proxy is useful for a hybrid diagnostic mode, and HarpCache's bounded/read-only/ignore-aware project snapshot is a reasonable context-injection design; neither should be required by the offline TUI. — [proxy](https://github.com/Achiral-AI/harp/blob/main/src/harp/proxy.py); [HarpCache](https://github.com/Achiral-AI/harp/blob/main/src/harp/harpcache.py)
7. **Do not reuse the unlicensed Python mock.** Its three-tool translation and DeepSeek reasoning cache are less complete than the current Rust implementation, while its absence of a license prevents safe copying. — [DeepSeek adapter](https://github.com/loongee/warp-local-proxy/blob/master/deepseek_client.py); [repository](https://github.com/loongee/warp-local-proxy)

### Inferences

- The lowest-risk integration boundary is: **TUI local mode → `crates/warp_local_server` only for `/ai/multi-agent`; TUI owns identity-free state, history, permissions, and tool execution.** This avoids coupling server evolution to the entire Warp cloud API surface.
- If the TUI still performs startup calls after auth is bypassed, capture those paths and either disable them in local mode or implement a typed local response. Do not begin with a catch-all success handler, because it converts contract mismatches into later, harder-to-debug state failures.
- Near-term code-review targets from Slipstream should be provider stream normalization and tool-history validation, not its full GraphQL/database layer.
- The best next implementation reference for login bypass is OpenWarp; the best next server reference is Slipstream.

### Gaps

- A precise TUI call graph under logged-out startup is still needed to decide whether any local GraphQL operation is unavoidable.
- The TUI may share auth assumptions with GUI code; the implementation must ensure local bypass is scoped to the local transport/channel and does not weaken authentication for normal Warp endpoints.
- MCP, long-running commands, background tasks, compaction, and model discovery remain optional follow-on scope rather than prerequisites for the first login-free DeepSeek session.
