Research date: 2026-10-03. Source review is pinned to default branch `byok` at commit [`3de21ef37fa93b3602cfe68b8c04d407052a5c39`](https://github.com/pixelkaiser/slipstream/tree/3de21ef37fa93b3602cfe68b8c04d407052a5c39), also the commit tagged `v0.1.36`. “Verified” below means observed in that revision’s code, rather than accepted solely from the README.

## Which Warp endpoints and protobuf/SSE semantics does it implement, and what are the backend’s architecture, provider, tool, and persistence boundaries?

### Takeaway

Slipstream is not merely a reverse proxy: it is a stateful Rust sidecar plus a large Warp GUI fork. The sidecar implements the key Warp multi-agent Protobuf/SSE exchange, a deliberately partial local GraphQL facade, local autocomplete, a broad client-executed tool bridge, and SQLite-backed provider transcripts. Its provider interface is specifically OpenAI-compatible streaming Chat Completions; it is not a provider-neutral Anthropic/Google adapter, and its DeepSeek-style reasoning treatment is weaker than our `warp_local_server` implementation.

### Cited Findings

#### Architecture and HTTP surface

- **Verified:** `crates/local_multi_agent_service` is an Axum service with `GET /health`, `GET /session/{session_id}`, `POST /ai/multi-agent`, `POST /ai/passive-suggestions`, `POST /ai/local-command-autocomplete`, and `POST /graphql/v2`. It binds to configured `HOST:PORT` (defaults are `127.0.0.1:8787`) and limits request bodies to 25 MiB. [Source: `server.rs` routes and bind](https://github.com/pixelkaiser/slipstream/blob/3de21ef37fa93b3602cfe68b8c04d407052a5c39/crates/local_multi_agent_service/src/server.rs#L31-L90); [source: defaults](https://github.com/pixelkaiser/slipstream/blob/3de21ef37fa93b3602cfe68b8c04d407052a5c39/crates/local_multi_agent_service/src/config.rs#L100-L180)
- **Verified:** `/health` returns JSON containing `ok`, crate version, and `configHash`; `/session/{id}` redirects to a custom URL scheme. This is more specific than our server’s current plain-text `ok`, so Slipstream’s process manager cannot reuse our health check without adjustment. [Source: health and redirect handlers](https://github.com/pixelkaiser/slipstream/blob/3de21ef37fa93b3602cfe68b8c04d407052a5c39/crates/local_multi_agent_service/src/server.rs#L111-L158)
- **Verified:** The local GraphQL handler recognizes a finite set of operations for simple integrations, OAuth status stubs, environment/repository stubs, generic string/cloud objects, model choices, user/settings metadata, conversations/usage, referrals, and workspace metadata; unknown operations return an explicit unsupported-operation response. It is therefore a compatibility facade, not an implementation of Warp’s full GraphQL backend. [Source: operation dispatch](https://github.com/pixelkaiser/slipstream/blob/3de21ef37fa93b3602cfe68b8c04d407052a5c39/crates/local_multi_agent_service/src/graphql.rs#L30-L93); [source: name inference/canonicalization](https://github.com/pixelkaiser/slipstream/blob/3de21ef37fa93b3602cfe68b8c04d407052a5c39/crates/local_multi_agent_service/src/graphql.rs#L129-L236)
- **README claim corroborated by code:** Slipstream describes “no-cloud” local inference, local GraphQL, local tools/MCP, and local state. Those broad claims correspond to real sidecar routes, SQLite tables, and client patches, though the TUI exception is material and covered in the next section. [Source: README claims](https://github.com/pixelkaiser/slipstream/blob/3de21ef37fa93b3602cfe68b8c04d407052a5c39/README.md#L48-L60)

#### Warp wire protocol

- **Verified:** `/ai/multi-agent` and `/ai/passive-suggestions` decode the body directly as `warp_multi_agent_api::Request` with Prost. A bad Protobuf body returns HTTP 400 JSON; a valid request gets HTTP 200 `text/event-stream` with no-cache/keepalive headers. [Source: request decode and SSE response](https://github.com/pixelkaiser/slipstream/blob/3de21ef37fa93b3602cfe68b8c04d407052a5c39/crates/local_multi_agent_service/src/server.rs#L316-L382)
- **Verified:** Each outbound SSE message is exactly `data: <URL-safe padded base64(Protobuf ResponseEvent)>\n\n`. Slipstream uses `base64::engine::general_purpose::URL_SAFE`, matching its patched client’s `BASE64_URL_SAFE` decoder. [Source: encoder](https://github.com/pixelkaiser/slipstream/blob/3de21ef37fa93b3602cfe68b8c04d407052a5c39/crates/local_multi_agent_service/src/response.rs#L121-L134); [source: client decoder](https://github.com/pixelkaiser/slipstream/blob/3de21ef37fa93b3602cfe68b8c04d407052a5c39/app/src/server/server_api.rs#L1282-L1307)
- **Verified:** Successful interactive sequencing is: `StreamInit`; optional `CreateTask` (and CLI subtask actions); first assistant chunk as `AddMessagesToTask`; later chunks as `AppendToMessageContent` with field mask `agent_output.text`; zero or more tool-call messages; final `StreamFinished.Done` with approximate context usage. Passive suggestions currently short-circuit after init and finish without provider inference. [Source: orchestration](https://github.com/pixelkaiser/slipstream/blob/3de21ef37fa93b3602cfe68b8c04d407052a5c39/crates/local_multi_agent_service/src/server.rs#L428-L655); [source: append field mask and finish events](https://github.com/pixelkaiser/slipstream/blob/3de21ef37fa93b3602cfe68b8c04d407052a5c39/crates/local_multi_agent_service/src/response.rs#L235-L369)
- **Verified:** Provider failures map to Warp terminal events for invalid key, unavailable LLM, context-window exhaustion, quota, or internal error, so the UI can leave the stream in a coherent terminal state rather than relying only on an HTTP error. [Source: mapping](https://github.com/pixelkaiser/slipstream/blob/3de21ef37fa93b3602cfe68b8c04d407052a5c39/crates/local_multi_agent_service/src/server.rs#L878-L887); [source: response constructors](https://github.com/pixelkaiser/slipstream/blob/3de21ef37fa93b3602cfe68b8c04d407052a5c39/crates/local_multi_agent_service/src/response.rs#L320-L370)
- **Verified:** Request decoding covers task/CLI context, current prompts, summaries, selected/attached context, images, MCP summaries, referenced attachments, and many typed tool results. This is materially broader request coverage than our initial `warp_local_server`, whose documented non-goals currently include subtasks, summarization, skills, referenced attachments, images, and MCP. [Source: Slipstream request decoder entry and typed result decoders](https://github.com/pixelkaiser/slipstream/blob/3de21ef37fa93b3602cfe68b8c04d407052a5c39/crates/local_multi_agent_service/src/request.rs#L108-L174); [source: tool-result decoding](https://github.com/pixelkaiser/slipstream/blob/3de21ef37fa93b3602cfe68b8c04d407052a5c39/crates/local_multi_agent_service/src/request.rs#L776-L1227)

#### Provider/model/reasoning behavior

- **Verified:** Provider calls are `POST {base_url}/chat/completions` with Bearer auth, `stream: true`, model/messages/temperature/max tokens, optional OpenAI function tools, and optional `chat_template_kwargs.enable_thinking`. Provider/model selection can be overridden per request via `X-Warp-*` headers, with environment configuration as fallback. [Source: provider request](https://github.com/pixelkaiser/slipstream/blob/3de21ef37fa93b3602cfe68b8c04d407052a5c39/crates/local_multi_agent_service/src/provider.rs#L149-L270); [source: header handling](https://github.com/pixelkaiser/slipstream/blob/3de21ef37fa93b3602cfe68b8c04d407052a5c39/crates/local_multi_agent_service/src/server.rs#L331-L365)
- **Verified:** Model discovery calls the OpenAI-compatible `GET /models`; if unavailable or empty, the service uses `LOCAL_MODEL_LIST`/`OPENAI_MODEL`. Warp “auto-*” model IDs are mapped through configurable aliases, while non-auto concrete IDs are preserved. [Source: model discovery](https://github.com/pixelkaiser/slipstream/blob/3de21ef37fa93b3602cfe68b8c04d407052a5c39/crates/local_multi_agent_service/src/provider.rs#L427-L468); [source: alias resolution](https://github.com/pixelkaiser/slipstream/blob/3de21ef37fa93b3602cfe68b8c04d407052a5c39/crates/local_multi_agent_service/src/model.rs#L1-L70)
- **Claim plus verification:** The README names LM Studio, vLLM, LocalAI, Ollama-compatible endpoints, and private gateways, but the implementation has one generic OpenAI-compatible path. There is special credential/provider labeling for xAI; there is no direct Anthropic Messages or Gemini API client. [Source: README provider list](https://github.com/pixelkaiser/slipstream/blob/3de21ef37fa93b3602cfe68b8c04d407052a5c39/README.md#L22-L32); [source: generic Chat Completions implementation and xAI special case](https://github.com/pixelkaiser/slipstream/blob/3de21ef37fa93b3602cfe68b8c04d407052a5c39/crates/local_multi_agent_service/src/provider.rs#L149-L180)
- **Verified limitation for DeepSeek:** The stream parser recognizes `delta.reasoning`, `reasoning_content`, and `reasoningContent`, but buffers them only as a fallback and emits them as ordinary output only when no public content appears; if normal content appears, the reasoning fallback is cleared. It does not emit Warp `AgentReasoning` events or preserve DeepSeek reasoning for a later tool-result request. [Source: stream loop behavior](https://github.com/pixelkaiser/slipstream/blob/3de21ef37fa93b3602cfe68b8c04d407052a5c39/crates/local_multi_agent_service/src/provider.rs#L273-L377); [source: reasoning field extraction](https://github.com/pixelkaiser/slipstream/blob/3de21ef37fa93b3602cfe68b8c04d407052a5c39/crates/local_multi_agent_service/src/provider.rs#L1585-L1604)
- **Verified:** It additionally filters Harmony-style internal/public channel markers and parses Harmony text-embedded tool calls, useful for some open-weight models. [Source: Harmony filter](https://github.com/pixelkaiser/slipstream/blob/3de21ef37fa93b3602cfe68b8c04d407052a5c39/crates/local_multi_agent_service/src/provider.rs#L1141-L1384)

#### Tools, MCP, and persistence

- **Verified:** The response translator emits client-side Warp calls for `run_shell_command`, `read_shell_command_output`, `read_files`, `grep`, `file_glob`, `search_codebase`, `apply_file_diffs` (including V4A updates), `suggest_plan`, `read_mcp_resource`, and `call_mcp_tool`. Unknown provider functions are accepted as native MCP only if exactly one request-context MCP tool has that name, avoiding ambiguous dispatch. [Source: tool enum and parse dispatch](https://github.com/pixelkaiser/slipstream/blob/3de21ef37fa93b3602cfe68b8c04d407052a5c39/crates/local_multi_agent_service/src/response.rs#L23-L80); [source: dispatch](https://github.com/pixelkaiser/slipstream/blob/3de21ef37fa93b3602cfe68b8c04d407052a5c39/crates/local_multi_agent_service/src/response.rs#L372-L390); [source: unique MCP match rule](https://github.com/pixelkaiser/slipstream/blob/3de21ef37fa93b3602cfe68b8c04d407052a5c39/crates/local_multi_agent_service/src/response.rs#L941-L964)
- **Verified:** MCP calls are not executed by the sidecar. The model is instructed to request the generic MCP wrappers; the sidecar encodes a Warp `Message.ToolCall`, and Warp returns the typed result on a subsequent request. [Source: MCP system prompt](https://github.com/pixelkaiser/slipstream/blob/3de21ef37fa93b3602cfe68b8c04d407052a5c39/crates/local_multi_agent_service/src/provider.rs#L931-L969); [source: client action encoding](https://github.com/pixelkaiser/slipstream/blob/3de21ef37fa93b3602cfe68b8c04d407052a5c39/crates/local_multi_agent_service/src/response.rs#L298-L317); [source: MCP result decoding](https://github.com/pixelkaiser/slipstream/blob/3de21ef37fa93b3602cfe68b8c04d407052a5c39/crates/local_multi_agent_service/src/request.rs#L1075-L1146)
- **Verified:** SQLite (Diesel) stores integration configurations, provider-format AI conversation transcripts, and generic string objects such as MCP/profile/preferences; WAL mode is enabled. Provider history is reloaded at startup, trimmed without orphaning tool-call/result groups, and replaced with one compacted summary system message after summarization. [Source: schema/init](https://github.com/pixelkaiser/slipstream/blob/3de21ef37fa93b3602cfe68b8c04d407052a5c39/crates/local_multi_agent_service/src/store.rs#L100-L151); [source: conversation load/save and compaction](https://github.com/pixelkaiser/slipstream/blob/3de21ef37fa93b3602cfe68b8c04d407052a5c39/crates/local_multi_agent_service/src/server.rs#L744-L875)

### Inferences

- For the current goal, Slipstream’s most valuable backend references are its **request-context decoder**, **additional tool/MCP codecs**, **summarization/compaction flow**, and **partial GraphQL operation inventory**. These can fill later feature gaps without replacing our already-tested DeepSeek-focused stream pipeline. [Supporting source: request decoder](https://github.com/pixelkaiser/slipstream/blob/3de21ef37fa93b3602cfe68b8c04d407052a5c39/crates/local_multi_agent_service/src/request.rs); [supporting source: GraphQL facade](https://github.com/pixelkaiser/slipstream/blob/3de21ef37fa93b3602cfe68b8c04d407052a5c39/crates/local_multi_agent_service/src/graphql.rs)
- We should **not wholesale replace** `crates/warp_local_server`: ours deliberately fixes exactly the DeepSeek semantics Slipstream lacks—first-class reasoning UI, `reasoning_content` round-trip through tool calls, provider redirect/credential restrictions, bounded concurrency/body/stream limits, disconnect cancellation, and typed validation. The more economical path is selective parity work only when the TUI needs those features.
- SQLite server-side transcripts are unnecessary for the first TUI integration because the current TUI sends complete task history. Persistence becomes attractive only for compaction, integrations, or clients that do not replay history; otherwise it creates a second authority that must remain consistent.

### Gaps

- No end-to-end TUI test or TUI-specific local inference example exists in the fork.
- I did not run Slipstream’s full test suite locally; maturity observations below come from source/test/workflow inspection and public release metadata.
- The fork does not document DeepSeek explicitly, and its generic OpenAI-compatible claim does not guarantee every vendor-specific request option will be accepted (for example, some providers reject `chat_template_kwargs`).

## What client patches redirect requests and bypass authentication, and do they cover `crates/warp_tui`?

### Takeaway

Slipstream has a real login-free/no-cloud path for its **GUI fork**, but it does **not** complete that work for Warp TUI. The reusable idea is a distinct local inference URL that skips access-token acquisition, plus a logged-out AI enablement override. The non-reusable parts are the fork-wide global server-root rewrite and fake/partial GraphQL surface. TUI still presents and enforces Warp device login.

### Inferences

- For our newer checkout, port the **concept**, not Slipstream’s code verbatim: current Warp moved transport into `crates/warp_multi_agent_client`, and the current TUI login model is substantially newer. The smallest safe integration is a TUI/local-agent mode that (1) marks the TUI interaction surface usable without a Warp identity, (2) allows AI while logged out, and (3) sends only multi-agent inference to `warp_local_server` without calling `BaseClient::get_or_refresh_access_token` or ambient-header resolution.
- Do **not** set global `ChannelState::server_root_url` to our `warp_local_server`: our server intentionally exposes only `/health` and `/ai/multi-agent`; global redirection would send auth, GraphQL, model/user metadata, update, sharing, and other calls to unimplemented routes. Slipstream can globally redirect only because it also carries the GraphQL facade and extensive no-cloud call-site patches.
- Do **not** synthesize a fake logged-in `AuthState` if a dedicated local TUI phase/capability can be added. A fake identity risks enabling Drive, sharing, team, billing, telemetry, and other account-only code. A local-access phase should activate the terminal/agent UI while cloud/account features remain unavailable.
- Process supervision is optional for the first wiring: the user already has `warp_local_server.exe`, so an explicit URL plus health check is less invasive than porting Slipstream’s bundled-child manager. Add supervision later only if distribution convenience matters.

### Gaps

- Slipstream does not show how to represent a login-free TUI state cleanly, so it offers no directly reusable solution for our current `TuiLoginModel`/`TuiLoginEvent` lifecycle.
- Slipstream’s TUI was at an earlier upstream revision; its `app/src/tui/mod.rs` cannot be cherry-picked onto the current checkout.
- The fork has no evidence that a signed-out TUI completed a real local-agent turn.

## Which parts should we reuse or avoid, and how mature/licensable is the project?

### Takeaway

Use Slipstream as a protocol and no-cloud design reference, not as a drop-in dependency or fork base. Its backend is unusually complete and test-rich, but the project is young, small, macOS-first, 141 commits divergent from a now-stale upstream base, and its local service is AGPL. For this checkout, targeted TUI transport/auth changes around our existing server have much lower merge and regression risk.

### Inferences

- **Recommended implementation sequence for our checkout:**
  1. Add an explicit TUI-local mode/URL (environment or CLI is sufficient initially).
  2. In that mode, initialize TUI into a non-account local-ready phase and create the terminal session, without mutating `AuthState` into a fake logged-in user.
  3. Extend `warp_multi_agent_client::generate_multi_agent_output` with a transport target/auth policy; local target uses `{url}/ai/multi-agent`, no access token, no ambient/team headers.
  4. Let `AISettings`/workspace capability checks permit the agent only under explicit local mode.
  5. Disable or short-circuit startup calls that still assume account/server metadata, one by one, rather than pointing them at the inference server.
  6. Test request routing/auth omission, logged-out TUI initialization, and a real render-to-lines/tool round trip against a local mock server; then perform live TUI verification.
- This preserves Warp TUI, permissions, and client tool execution while eliminating the Warp service dependency for the requested flow. It also leaves a clean boundary for future hosted login use when local mode is off.
